## 2. 这一天做了什么（按依赖顺序，不是时间顺序）

### 2.1 先把「三条通道」分清

此前一直把 BLE GATT 和 RFCOMM 当成同一件事的不同承载。这次做了**信道 × 协议矩阵**：

```
ch1  连接失败   [WinError 10048]
ch2  已连接     "AT+BRSF=671\r"  ← HFP，与我们无关
ch3  连接失败   [WinError 10064]
ch4  连接失败   [WinError 10064]
ch5  已连接     零字节回包
ch6  已连接     ★ Mate 握手有回包，读 142 有回包  ← 唯一真正可用的通道
ch7..ch15       连接失败   [WinError 10064]
```

**关键发现**：在 ch6 上，紧邻着成功应答的 Mate 帧之后发 GAIA 帧，**零回包**。

```
ch6  Mate 握手            -> 00 27 02 00 03 ff 01 ff     ★
     读 142               -> 01 27 02 00 03 8e 01 00      ★
     GAIA GET_STATUS(16394)     -> (空)                   ★ 零回包
     GAIA GetCodingAndDecodingType(1954) -> (空)          ★ 零回包
     再读 142             -> 02 27 02 00 03 8e 01 00      ★ 链路正常
```

链路正常、Mate 正常、GAIA 零回包 → **不是链路问题，是固件不实现 GAIA**。

**根因也找到了**：`FiilManager.a()` 按 `earType` 分派命令类，`46` 没有任何分支命中，
落到最内层 `default` → `FiilCommandF002`，而 `setUnlockLDAC` 在基类里是**空实现**。

**作废的整条路线**：文件系统 dump（`OPEN_FILE` 16385 / `READ_FILE` 16387）、
鉴权位图（`GET_AUTH_BITMAPS` 1408）、GAIA 侧解锁（`SetUnlockLADC` 1968）、
试用模式（12308/12309）、`GET_DISK_SPACE`（16399）、全部 `FFCOMMAND_*`。

### 2.2 首次真正执行 `cid=36`（恢复出厂）

历史记录里有一句自我更正：

> 「后来用正则 `\b[0-9a-f]{2} 24 01 00\b` 重扫全部日志，`cid=36` **一次都没真正发出过**。」

但同一份文档的另一处仍写着「发了恢复默认值后 142 仍为 0」——**那是建立在已被否证的前提上的结论**。
所以这次真的发了：

```
TX  00 24 01 00 00
RX  0A 24 02 00 01 00        ← payload[0]=00，被接受
```

| 项 | 恢复前 | 恢复后 |
|---|---|---|
| `142` 授权 | `00` | `00` ← **不动** |
| `143` 开关 | `01` | `00` ← 被重置 |
| `144` codec | `01` | `02` ← 变化 |
| 固件/校验和/UUID/能力位 | — | 全部不变 |

**意外收获**：恢复出厂后，紧接着的 **17 次 SET 全部 `ACK=01` 被拒**——
包括 `setTone` / `setTipVolume` / `multiConnect` / `setLDAC`，连官方零值取消激活都被拒。
这是**第一次看到 `ACK` 不是 00**。

试了 5 种自救（握手后立刻写 / 连写 3 次 / 读完设备信息再写 / 重新握手再写 / 探测 cmd 0-255），全部失败。
**断电重启后立即恢复**（`setLDAC(1)` 回 `ACK=0`）。

→ 恢复出厂的「写全拒」是**临时状态**。

### 2.3 把 `ACK` 的语义钉死

看到 `ACK=01` 之后，第一反应是「`ACK` 可能是内容校验的 oracle」，于是做了 18 个候选的矩阵：

| 候选 | `ACK` |
|---|---|
| 17 字节全零 | 0 |
| 真 UUID license（side=0/1） | 0 / 0 |
| 全 `FF` ×17 | 1 |
| 全 `AA` ×17 | 1 |
| 全 `01` ×17 | 0 |
| 空 payload（len=0） | 1 |
| 单字节 `00` / `01` | 1 / 1 |
| 16 字节裸 UUID（无 side） | 1 |
| 18 字节 `side0+UUID+00` | 1 |
| 17 字节 `side=2` / `side=FF` | 1 / 1 |
| 17 字节 `side0 + 全零UUID` | 0 |
| 反转 UUID + side0 | 0 |
| 17 字节随机（`00 + 11..20`） | 0 |

**规则只有两条**：`len == 17` 且 `payload[0] ∈ {0x00, 0x01}`。
**内容完全不参与。** `ACK` 不能当 oracle。

### 2.4 ★ 发现 140 / 141 是 license 存储槽

这是这一天最重要的一次「原来我一直在看错地方」。

做法：写前扫 `info 0..255`，写左右耳 license 后再扫一遍，**逐项 diff**。

```
写前：140 = 141 = 11 12 13 14 15 16 17 18 19 1a 1b 1c 1d 1e 1f 20
写后：140 = 141 = 42 50 32 36 32 30 35 12 00 3b 51 45 06 20 bb 78
（其余 254 项全等；138/139 设备 UUID 未变；142 仍 00）
```

那串 `1112...20` 正是我之前写进去的「17 字节随机」候选去掉 side 字节后的 16 字节。

**性质逐条验证**：

| 性质 | 结果 |
|---|---|
| 可写 | ✅ |
| 可持久化 | ✅ 断链重连后内容仍在（真落盘） |
| 精确回显 | ✅ 写什么读回什么 |
| `side` 的作用 | **只做路由**：写 side=0 或 side=1 都同时改 140 和 141 |
| 与 138/139 的关系 | **无关**。138/139 只读，任何写入都不影响 |
| `cid=39` 侧能否写 | ❌ 只读镜像（带数据发 `cmd=0x8C`，回包原值，槽未变） |

**但 142 不是它的函数。**（见 2.6）

### 2.5 ★★ 帧形状：我错了整整一轮

发现 140/141 可写之后，立刻在「正确位置」上穷举。但**全部 `ACK=1`**。

一度以为「写入通道被锁死」，做了半天救援。转折点是一次 A/B 对照：

```
S1  setLDAC(1) 官方形状  cid=1 cmd=13 payload=[01]          → ACK=0  ★
S2  setLDAC(1) 错误形状  cid=1 cmd=12 payload=[13,1,1]      → ACK=1
T2  setLDAC(0) 官方形状  cid=1 cmd=13 payload=[00]          → ACK=0，143 变 00  ★
```

**`setLDAC` 是 `cmd=13`，1 字节 payload。** 我用 `cmd=12` 发它，当然 `ACK=1`。

顺着这条线查下去，发现 license 的帧形状也错了：

```java
// 官方 F046（c.java）：buffer = 17 字节裸 license
//   → 帧 = 00 01 01 00 13 0C 11 <side><16B>     ✅
//
// 我用的：[12, 17, side] + 16B
//   → 帧 = 00 01 01 00 15 0C 13 0C 11 <side><16B>   ✗
```

`[12, 17]` 是 `F39AppSettingRequest.setActivateLdac()` 自己加的前缀，
**那是 F048 / CC Pro2 的形状，不是 F046 的。**

对照验证：

| 测试 | 帧 | `ACK` | 槽位被改写 |
|---|---|---|---|
| W1 | 17B 裸帧 `[00]+A0..AF` | **0** | ✅ `140=141=a0..af` |
| W2 | 19B 前缀 `[12,17,00]+A0..AF` | 1 | ❌ |
| W3 | 17B 裸帧 `[01]+B0..BF` | **0** | ✅ `140=141=b0..bf` |
| W4 | 19B 前缀 `[12,17,01]+B0..BF` | 1 | ❌ |

**这一条纠正了此前所有 19 字节形状的穷举结果**——那些 `ACK=1` 不是「内容被拒」，是**帧根本没被解析**。

### 2.6 ★ 写 → 真重启 → 回读：从来没做过的复核

历史 5000+ 次写入，复核全部是「同一次连接内」或「断链重连」。
**从没做过真重启后回读。** 如果固件把 142 缓存在 RAM、boot 时按槽位内容重算，只有重启才看得到。

用 `cid=36` 触发重启，重连后立刻回读：

```json
{"base":                {"140":"4250...bb78","141":"同上","142":"00","143":"01","144":"02"},
 "after_write":         {"140":"4250...bb78","141":"同上","142":"00","143":"01","144":"02"},
 "reboot_A_after_uuid": {"140":"4250...bb78","141":"同上","142":"00","143":"00","144":"02"},
 "reboot_B_after_zero": {"140":"0000...0000","141":"全零","142":"00","143":"01","144":"02"}}
```

写 license → 重启 → 回读：**142 仍 `00`**（槽位确实落盘）。
对照组写全零 → 重启 → 回读也是 `00`。

**→ 142 不是 140/141 内容的函数，固件不在 boot 时按槽位重算。**

## 4. 这一天的判断失误（承接 `research/README.md` 第 5 节）

前三次失误已在原文档记过。这次新增四条：

**失误 5 · 用 `cmd=12` 发 `setLDAC`，然后断定「写入通道被锁」**

错误结论持续了约半小时，期间做了「5 种自救」这种完全无意义的动作。
教训：**A/B 对照要同时试「正确形状」和「错误形状」**，只试一种会把「我用错了」误判成「设备坏了」。

**失误 6 · 把 F048 的 `[12,17]` 前缀套到 F046 上**

这是整次研究里最贵的一个错误。它让**所有** license 穷举在错误的帧上跑了一遍，
`ACK=1` 被我读成「内容被拒」，而实际是「帧结构不被解析」。

教训：**同一个功能在不同机型上可能有两套完全不同的帧形状。**
在跨机型复用代码之前，必须先确认目标机型的命令类（F046 是 `c.java`，F048 是 `e.java`），
而不是看「功能名相同」就套。

**失误 7 · 认为 140/141 只是「UUID 变更通知通道」**

因为它们在早期扫描里没有回包（落在 `25..127` 段全部 no-reply），就下了「不是读口」的判断。
**但只要写一次再看 diff，就能发现它们就是 license 槽。**

教训：**「读不到」不等于「不存在」**。全空间差分是比单点查询强得多的取证手段。

**失误 8 · 相信了 `research/README.md` 里那条自己已经否证过的结论**

文档一处写「`cid=36` 一次都没真正发出过」，另一处仍写「发了恢复默认值后 142 仍为 0」。
我没先核对就直接引用了后者。

教训：**文档内部矛盾时，以「可复现的原始帧」为准**，不以「结论叙述」为准。

**失误 9 · 把两套 `cid=1` 写接口当成同一套（2026-11-17 才查清）**

APK 里存在两套互不兼容的 `cid=1` 写接口：

| | 体系 A（F046 实际用） | 体系 B（F048 / CC Pro2） |
|---|---|---|
| 类 | `com.fengeek.main.i.d.{b,c,d,e,f,g,h}` | `F39AppSettingRequest` |
| 形态 | `cmdId` 直接区分命令，payload 各自定义 | **固定 `cmd=12`**，payload = `[type, 1, value]` |
| F046 用不用 | ✅ 全部设置走这套 | ❌ 零调用 |

我在「ACK 语义标定」实验里，把体系 B 的三字节 `[cmd,1,v]` 发到了体系 A 的 cmdId 上，
于是 17 次 SET 全部 `ACK=01`，我又据此推出「恢复出厂锁死了写入通道」。

真正被这条污染的结论有三个：
1. **恢复出厂锁写入**（§3.6，已降级）；
2. **延迟生效否证** —— `probe_license_delayed.py:195` 发的是 19 字节
   `[12,17,side,UUID]`（体系 B 的 `setActivateLdac` 形状），`ACK=1` 说明根本没被接受，
   所以「53 秒不回读」什么也没证明；
3. **143 是前置条件否证** —— A/B 对照用的同样是 19 字节前缀帧。

**没有**被污染的（逐脚本核实过，发的是正确的 17 字节裸帧）：
`sweep_single_byte.py:159-172`（4335 全扫）、`sweep_correct_shape.py:97-100`（410 候选）、
`sweep_keyed.py:118-120`（88 候选）、`probe_boot_recompute.py:87`（写→重启→回读）。
这四个的结论**仍然有效**。

教训：**同名的 `cid` 可能有多套封装。先确认机型走哪个命令类
（`FiilManager.a()` 的 earType 分派表），再看那个类的 `set*` 方法，别跨类拼表。**
另外，`ACK`/返回值这类「看起来能当判据」的东西，一定要先用一个**已知必然成功**的命令做基线，
否则会把形状错误读成设备拒绝。

## 7. 判断

> **2026-11-17 补一句给未来的自己**：写「封死」时要先问一句
> 「我是用**正确**的帧形状封死的吗」。这一天有 3 条排除栽在这上面。

**和前一阶段一致：这条路在协议层是封死的。**

差别在于，前一阶段说「封死」是**基于一堆没做对的复核**；
这一阶段说「封死」，是**每一步都有原始帧、有 diff、有 A/B 对照**——
但其中三条的对照本身用错了帧形状（见失误 9），所以这个「封死」的**准确边界**是：

| 已经过正确帧形状验证、可以当结论的 | 证据链被污染、需重测的 |
|---|---|
| license = 设备 UUID（17B 裸帧） | 延迟生效否证（用了 19B 前缀帧） |
| license = UUID 单字节变体（4335 次，17B 裸帧） | 143 是否写 license 的前置条件（同） |
| license = 常量/哈希派生（410 候选，17B 裸帧） | 恢复出厂是否锁写入通道（用了 3B 错误形状） |
| license = App 内密钥派生（88 候选，17B 裸帧） | |
| 写 → 真重启 → 回读（17B 裸帧） | |
| GAIA 在 F046 上不存在（零回包） | |
| 140/141 是 license 槽（全 info 差分） | |

**142 不是 UUID 的函数，不是槽位内容的函数。**
「不是时序的函数」这条**暂时只能算强怀疑**，要等重测。
剩下只有「未暴露的存储位置」和「固件内密钥」两种可能，两条都需要拿到固件。

在那之前，**不建议再在协议层尝试写 142**。
